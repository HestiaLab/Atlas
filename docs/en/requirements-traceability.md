Before the first functional work package is merged, all 151 formal
requirements default to `Not Started`. After implementation begins, only the
Requirements whose status changes are recorded below; a Requirement without an
explicit record remains `Not Started`.

The P8 item-by-item audit is in the
[151 formal requirement status table](./evidence/p8-requirement-audit.md).
That table has exactly one row per formal ID and explicitly keeps Partial,
Not Started, and Deferred gaps.

## Status

| Status | Meaning |
|--------|---------|
| Not Started | No functional implementation yet |
| In Progress | Has an active work package; not all ACs are satisfied yet |
| Implemented | Code is complete, but verification evidence is not fully passing yet |
| Verified | The matching automated verification passed and no open blocker remains |
| Blocked | Blocked by an Open Issue, DEV-GATE, or external decision |

`Designed` is an HLD status, not an implementation status; it must not be
converted directly to `Implemented` or `Verified`.

## Update Rules

1. Every functional PR must list Requirement, DES, Phase, owner module, and
   tests.
2. When a Requirement has multiple ACs, it may only be marked `Verified` when
   every AC has evidence.
3. Open/Partial/Deferred requirements must not be marked `Verified` with
   partial implementation.
4. Refactoring does not change requirement status; behavior changes must go
   back through SRS/HLD review.
5. When test paths or public API change, this file and the code are updated in
   the same commit.
